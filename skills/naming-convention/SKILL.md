# 全体の命名規則

このドキュメントは、プロジェクト全体で利用する命名規則を定義する。

## 基本方針

- 名前は「役割」と「責務」がわかるものにする。
- 省略語はチームで共通認識があるもののみ使う。
- 文脈で意味が変わる曖昧な名前（`data`、`info`、`temp` など）を避ける。
- 命名は実装時だけでなく、リファクタリング時にも適用する。

## ファイル名・ディレクトリ名

- ファイル名・ディレクトリ名は `kebab-case` を使用する。
- 機能単位でまとまりを作り、`misc` や `utils2` のような曖昧な名前を避ける。

## 型名・クラス名・インターフェース名

- 型名・クラス名・インターフェース名は `PascalCase` を使用する。
- 型はドメイン用語で命名し、用途が伝わる接尾辞（`Dto`、`Schema` など）を必要時のみ付与する。
- 真偽値を表す型や列挙値は意味が伝わる語を使い、否定語の二重表現を避ける。

## 変数名・定数名

- 変数名は `camelCase` を使用する。
- 定数はプロジェクト規約に合わせ、必要な場合のみ `UPPER_SNAKE_CASE` を使用する。
- 真偽値は `is` / `has` / `can` で始める。
- 配列は `userList` のように複数形にせず、`List` を付けて表す。
- 短縮語はなるべく使わず、意味が伝わる名前にする。

## 関数名

### 取得系

- `find〇〇`
  - 単体を取得するときに使う
- `get〇〇List`
  - 複数を取得するときに使う
  - `get` の後は複数形にせず、`List` で表現する

### 更新系

- `create〇〇`
  - 新規作成で使う
- `edit〇〇`
  - 既存データの更新で使う
- `upsert〇〇`
  - 存在すれば更新、なければ作成で使う
- `delete〇〇`
  - 物理削除（完全削除）で使う
- `archive〇〇`
  - 論理削除で使う
  - 物理削除の `delete` と区別するため、論理削除は `archive` を使う
- `publish〇〇`
  - 公開状態にするときに使う
- `save〇〇`
  - Repository 関数で、作成・更新・削除をまとめて扱うときに使う

### Util、ドメインロジック系

- `generate〇〇`
  - ランダム文字列やオブジェクトなど、何かを生成するときに使う
- `calculate〇〇`
  - 計算して値を算出するときに使う
- `construct〇〇`
  - ドメインモデルの組み立て、パース、ルールチェックで使う
- `hydrate〇〇`
  - DB データをドメインモデルへ変換するときに使う
- `validate〇〇`
  - バリデーションをし、`boolean` を返す関数
- `check〇〇`
  - 何かをチェックし、`boolean` を返す関数

## エラータグ

### 基本ルール

- エラーは `TaggedError` を使って実装する。
- タグ名は `UPPER_SNAKE_CASE` を使用する。

### タグの具体例

- データに不備があるとき: `INVALID_{対象}`
- データが存在しないとき: `NOT_FOUND_{対象}`
- 同一データが既に存在するとき: `DUPLICATE_{対象}`
- 既に何らかの処理が行われているとき: `ALREADY_{過去分詞}_{対象}`
- 認証エラー: `UNAUTHORIZED_ERROR`
- 予期しないエラー: `UNEXPECTED_ERROR`
