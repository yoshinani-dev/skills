# コードコメント規約

このドキュメントは、プロジェクト全体で利用するコメントの方針と判断基準を定義する。

## 基本方針

- **コードは自己説明的であることを優先する。** コメントで補うのではなく、命名・構造・関数分割で意図を伝える。
- コメントは「なぜ（Why）」を説明する。コードを読めばわかる「何を（What）」は書かない。
- コメントは実装と同期させる。古くなったコメントは削除または更新する。
- コメントで仕様を書きすぎない。詳細な仕様は `specs/` やドキュメントに置き、コードには要点だけ残す。

## 書くべきコメント

### ビジネスロジック・ドメイン知識

- コードだけでは推測できない業務ルール・制約・例外処理の理由
- 外部仕様（法令・会計ルール・第三者 API の制約など）に基づく判断

```typescript
// NOTE: freee の仕様上、取引先コードは一度発行すると変更できない
```

### 非自明な技術的判断

- パフォーマンス上の理由で通常と異なる実装をしている箇所
- セキュリティ・整合性のための意図的な制約
- ライブラリやランタイムの挙動に依存する回避策

```typescript
// NOTE: N+1 を避けるため、ここでは join ではなく一括取得にしている
```

### ワークアラウンド・暫定対応

- 既知のバグ・制限に対する回避策（関連する Issue やコメントなどの URL を添える）
- 将来削除・置き換え予定の暫定実装

```typescript
// TODO: upstream 修正後に削除する https://github.com/org/repo/issues/123
```

上記のうち、意図・設計・特別な考慮事項は `NOTE:`、未対応・後回しの作業は `TODO:` を使う（[TODO / NOTE](#todo--note) を参照）。

### 公開 API・再利用される関数

- 他モジュールから呼ばれる export 関数・型には JSDoc / TSDoc を付ける
- 引数・戻り値・エラー条件・副作用を簡潔に記載する

## 書かないべきコメント

- コードをそのまま言い換えた説明

```typescript
// ❌ ユーザー ID を取得する
const userId = getUserId();

// ❌ ループで各アイテムを処理する
items.forEach(processItem);
```

- 削除済み・無効化されたコードのコメントアウト（Git 履歴に任せ、削除する）
- 変数名・関数名で十分に意図が伝わる箇所への冗長な補足
- 実装詳細の長文説明（ドキュメントや `specs/` に移す）

## 言語・表記

- **コメント本文は日本語**で書く（`type` / `scope` / 識別子などコード上の名前は英語のまま）。
- インラインコメントのプレフィックスは `NOTE:` と `TODO:` のみ。
- 1 コメント 1 意図。複数の論点は分割するか、関数・ブロックを分ける。
- 敬体（です・ます）は使わず、**常体（である・する）** で統一する。
- 句読点は省略してよい。短く端的に書く。

## JSDoc / TSDoc

export される関数・型・定数に付与する。

```typescript
/**
 * サイト ID をエンコードして URL 用の文字列に変換する。
 *
 * @param siteId - 内部で使う UUID 形式のサイト ID
 * @returns Base58 エンコードされた ID
 */
export function encodeSiteId(siteId: SiteId): EncodedSiteId {
  // ...
}
```

- `@param` / `@returns` は型と重複しない範囲で、**意味や制約**を補足する
- 例外や `TaggedError` を返す場合は、返却条件を本文に書く
- 自明な getter や 1 行ラッパーには JSDoc を付けない

### utility 関数

utility 関数は呼び出し側が内部実装を知る必要がない。**何をする関数か・引数に何を渡すか・何を返すか**を JSDoc で明記する。実装の詳細（アルゴリズムや内部のデータ構造）は書かない。

```typescript
/**
 * 住所文字列から郵便番号（ハイフンなし 7 桁）を抽出する。
 * 見つからない場合は `null` を返す。
 *
 * @param address - 都道府県・市区町村を含む住所文字列
 * @returns 7 桁の郵便番号。抽出できないときは `null`
 */
export function extractZipCode(address: string): string | null {
  // ...
}
```

### 非推奨（`@deprecated`）

使うのが非推奨になった export 関数・型・定数には `@deprecated` を付ける。`@deprecated` の直後に、**呼び出し側がどうすればよいか**（代替の関数・型・移行先）を書く。

```typescript
/**
 * @deprecated encodeSiteId を使用する
 */
export function encodeSiteIdLegacy(siteId: SiteId): string {
  // ...
}
```

- 代替がない・削除予定のみの場合も、理由と次のアクションを書く（例: `@deprecated v2 リリースで削除予定。新規利用はしない`）
- 非推奨にしたら、呼び出し元の移行を `TODO` で追跡する（関連 URL を併記する）

## TODO / NOTE

インラインコメントのプレフィックスは **`TODO`** と **`NOTE`** のみを使う。`FIXME` や `HACK` は使わない。

| プレフィックス | 用途                                                   |
| -------------- | ------------------------------------------------------ |
| `NOTE`         | コードの重要な意図、設計上の決定、特別な考慮事項の説明 |
| `TODO`         | 未実装・後で対応する改善・既知の不具合の修正予定       |

```typescript
// NOTE: 論理削除済みレコードは一覧に含めない（監査要件）
// NOTE: 親 feature から子 feature への一方向依存を守るため、import はここに集約する
// TODO: upstream 修正後にこのワークアラウンドを削除する https://linear.app/team/issue/TSK-123
```

- `NOTE` は「なぜこの実装なのか」が読み手に伝わるときに付ける
- `TODO` には、関連する Issue・PR コメント・タスクなどの **URL** を併記する（番号だけの記載はしない）
- 対応完了後は `TODO` を削除する。`NOTE` は設計が変わったら更新または削除する

## レイヤー別の目安

| レイヤー           | コメントの重点                                               |
| ------------------ | ------------------------------------------------------------ |
| `domain/`          | ビジネスルール、不変条件、ドメイン上の例外理由               |
| `read/` / `write/` | 外部依存の制約、トランザクション境界、パフォーマンス上の理由 |
| UI コンポーネント  | アクセシビリティ上の意図、デザインシステムから外れる理由     |
| テスト             | テストの意図（再現条件・エッジケース）のみ。実装の説明は不要 |

## 実装・レビュー時のチェックリスト

- [ ] コメントなしでも読めるコードになっているか（命名・分割で改善できないか）
- [ ] コメントは「Why」を説明しているか
- [ ] 古い・誤ったコメントが残っていないか
- [ ] コメントアウトされたコードが残っていないか
- [ ] export API に必要な JSDoc があるか
- [ ] 非推奨の API に `@deprecated` と代替手段が書かれているか
- [ ] 意図・設計・特別な考慮事項に `NOTE:` が付いているか
- [ ] `TODO` に関連 URL（Issue・コメント・タスクなど）が貼られているか
