# コミット

## When to Use

ユーザーが次のような意図で話したとき、このスキルを適用する:

- 「コミットして」「ステージして」「git commit」「コミットメッセージ」
- 「Conventional Commits で」「コミット文を書いて」「メッセージどう書く」
- 作業完了後に PR まで出す流れの **第1段階（コミット）** として（続けてそのリポジトリの submit-pr で PR）
- 変更を確定する前に、形式・手順・分割の判断が必要なとき

## 概要

変更内容に合った **Conventional Commits** 形式でメッセージを組み立て、`git add` / `git commit` を行う。PR を出すリポジトリでは、 `skills/submit-pr` と併用し、履歴と PR 本文のトーンを揃える。

根拠・詳細は [Conventional Commits 1.0.0（日本語）](https://www.conventionalcommits.org/ja/v1.0.0/) を参照。仕様上の **タイトル**（1行目の短い要約）に相当するものを、このスキルでは **件名** と呼ぶ。

**件名・本文の言語**: **日本語で統一**（`type` と `scope` は英語のまま）。

**破壊的変更**があるときは仕様どおり `feat(api)!:` のように `!` を付けるか、本文のあとに `BREAKING CHANGE: ...` フッターを書く（上記公式の「例」を参照）。

## 作業完了後のフロー（標準）

コードを書くリポジトリでは、**作業が完了したら次の順で進める**（あいでんの運用方針）。

1. **このスキル（commit）** — `git add` / `git commit` まで。Conventional Commits で履歴を残す。
2. **submit-pr スキル** — 同じリポジトリ内の `skills/submit-pr/SKILL.md`に従い、PR 本文の作成・更新と PR 作成まで。

commit メッセージと PR 本文のトーン・関連 Issue の書き方を揃える。secretary のようなドキュメント中心リポジトリで PR を出さないときは、手順 1 のみでよい。

## 先に確認すること（リポジトリごと）

プロジェクト固有のルールが **このスキルより優先**。

1. **文書**: `AGENTS.md`、`CONTRIBUTING.md`、`docs/` 内の開発ガイド、`.github/PULL_REQUEST_TEMPLATE.md` 近辺
2. **自動チェック**: `commitlint.config.*`、`.husky/`、`lefthook`、CI の lint ジョブ
3. **package.json の scripts**: `lint` / `test` / `check` / `format` など、コミット前に求められているもの
4. **言語の例外**: 公開 OSS やクライアント共有で英語必須のときは、既存ログ・ルールに合わせる（不明なら **質問する**）

不明点があれば推測で進めず、**ユーザーに確認する**。

## 使用するコマンド

```bash
# 変更の確認
git status
git diff

# ステージング（必要なファイルだけ）
git add <path>
# または対話的に
git add -p

# コミット（複数行本文が必要なとき）
git commit -m "$(cat <<'EOF'
<type>(<scope>): <件名（日本語・50文字目安）>

<本文: なぜ・何を。任意。72文字で折り返し>
EOF
)"

# 1行で十分なとき
git commit -m "<type>(<scope>): <件名>"
```

## テンプレート

```text
<type>(<scope>): <件名（日本語）>

<空行>
<本文1行目（任意・日本語）>
```

### 例

```text
feat(web): 会員情報フォームにバリデーションを追加

Zod スキーマと一致させ、送信前にエラーを表示する
```

```text
fix: 一覧のページネーションが0件になる不具合を修正

オフセット計算のオフバイワンを解消
```

```text
docs: AGENTS に Cursor Cloud の注意点を追記
```

```text
feat(api)!: 認証レスポンスのフィールド名を変更

BREAKING CHANGE: `user_id` を `userId` に統一。クライアントの型定義を更新すること
```

## メッセージの型（type）

| type       | 用途                                   |
| ---------- | -------------------------------------- |
| `feat`     | 新機能                                 |
| `fix`      | バグ修正                               |
| `docs`     | ドキュメントのみ                       |
| `style`    | 見た目・フォーマット（挙動は変えない） |
| `refactor` | リファクタ（機能追加・修正ではない）   |
| `test`     | テストの追加・修正                     |
| `chore`    | ビルド・補助ツール・依存更新など       |
| `build`    | ビルドシステムや外部依存の変更         |
| `perf`     | パフォーマンス改善                     |
| `ci`       | CI 設定                                |

チームが別の型を使っている場合はそちらに合わせる。

## スコープ（scope）

**任意**。モノレポならパッケージ名・アプリ名（例: `web`, `api`, `ui`）、単一パッケージなら省略が多い。既存コミットの付け方に合わせる。

## 件名のルール（日本語）

- **体言止め** または **「〜する」調** で簡潔に（チームで統一しているならそれに従う）
- 末尾の句点は付けないことが多い（チーム運用に従う）
- 50 文字前後を目安（長い説明は本文へ）

## チェックリスト

コミット前に確認:

- [ ] 意図しないファイル（`.env`、秘密情報、生成物、個人メモ等）が含まれていない
- [ ] このリポジトリが求める **lint / test / format** を実行した（または CI に任せる方針を把握している）
- [ ] `type` が変更内容と一致している
- [ ] 件名が具体的で、単独で読んでも分かる
- [ ] 破壊的変更がある場合は `!` または `BREAKING CHANGE:` で明示した（該当するとき）
- [ ] 無関係な変更を 1 コミットに詰め込んでいない（可能なら分割）

## このスキルの置き場所

**このリポジトリ（secretary）の** [.cursor/skills/commit/SKILL.md](SKILL.md) **を正本とする。** 他プロジェクトではコピーするか、グローバル `~/.cursor/skills/commit/SKILL.md` を併用してよい。PR 本文は各リポジトリの `submit-pr` 等に従う。

| 置き場所                                      | 効く範囲                         |
| --------------------------------------------- | -------------------------------- |
| `secretary/.cursor/skills/commit/SKILL.md`    | 本ワークスペース（このファイル） |
| `~/.cursor/skills/commit/SKILL.md`            | 個人の全ワークスペース           |
| `<リポジトリ>/.cursor/skills/commit/SKILL.md` | そのリポジトリを開いたとき       |

リポジトリごとにルールを足すときは、**追記セクション**で上書きする。

## 関連

- **次のステップ**: コミット後に PR を出すときは、そのリポジトリの `skills/submit-pr/SKILL.md`に従う（**作業完了後のフロー（標準）** の手順 2）
- [Conventional Commits 1.0.0（日本語）](https://www.conventionalcommits.org/ja/v1.0.0/) — 型・スコープ・タイトル・本文・フッター、`BREAKING CHANGE` の定義
- PR 本文を書くときは、そのリポジトリの `skills/submit-pr`や `.github/PULL_REQUEST_TEMPLATE.md` とメッセージのトーンを揃える
- ブランチ名・レビュー運用は README / チームルールに従う
